# Triage

Move issues through a small state machine of triage roles. Distilled from Matt Pocock's `triage` skill, adapted to Hermes's runtime-agnostic posture.

## When to invoke

- Operator says "triage this", "let's process the backlog", "what needs my attention".
- An issue is being assessed against the state machine for the first time.

## Prerequisites

- An issue tracker is configured (see `to-issues`).
- The repo's triage label vocabulary is known. If unclear, ask the operator before applying any label.

## Roles

Two **category** roles:
- `bug` — something is broken.
- `enhancement` — new feature or improvement.

Five **state** roles:
- `needs-triage` — maintainer needs to evaluate.
- `needs-info` — waiting on reporter for more information.
- `ready-for-agent` — fully specified, ready for an AFK agent.
- `ready-for-human` — needs human implementation.
- `wontfix` — will not be actioned.

Every triaged issue carries exactly one category and one state. If states conflict, flag it and ask the operator before changing anything.

## Disclaimer rule

Every comment or issue posted by the agent during triage must start with:

```
> *This was generated by AI during triage.*
```

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:
1. Unlabeled — never triaged.
2. `needs-triage` — evaluation in progress.
3. `needs-info` with reporter activity since the last triage notes — needs re-evaluation.

Show counts and a one-line summary per issue. Let the operator pick.

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, labels, reporter, dates). Parse any prior triage notes so resolved questions are not re-asked. Explore the codebase using the project's domain glossary.
2. **Recommend.** Tell the operator your category and state recommendation with reasoning, plus a brief codebase summary relevant to the issue. Wait for direction.
3. **Reproduce (bugs only).** Before any grilling, attempt reproduction. Report what happened: confirmed repro with code path, failed repro, or insufficient detail (which is a strong `needs-info` signal).
4. **Grill (if needed).** If the issue needs fleshing out, run a `grill-with-docs` session.
5. **Apply the outcome:**
   - `ready-for-agent` — post an agent brief comment with reproduction steps, scope, and any constraints.
   - `ready-for-human` — same shape, but note why it cannot be delegated.
   - `needs-info` — post triage notes capturing what is established so far and what is still needed from the reporter.
   - `wontfix` (bug) — polite explanation, then close.
   - `wontfix` (enhancement) — capture the rejection rationale so future triage doesn't re-suggest it, then close.
   - `needs-triage` — apply the role. Optional comment if there's partial progress.

## Quick override

If the operator says "move #42 to ready-for-agent", trust them. Confirm what you are about to do (role change, comment, close) and then act. Skip grilling.

## Discipline

- Never apply a label without operator confirmation unless the operator has pre-authorized the role change in this session.
- Do not close issues silently. Every close action carries either a public rationale or an internal triage note.
- Triage findings belong in the Hermes report at the end of the session.
